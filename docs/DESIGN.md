# 音频桥 · Audio Bridge（原「显示器音频桥」）

把一台电脑**正在播放的系统声音**，通过局域网实时送到另一台电脑的扬声器/耳机。
Mac、Windows 各一个带界面的程序，**每一端都可以选「接收」或「发送」**，四种组合都支持：

```
Windows ──► Mac      Mac ──► Windows      Mac ──► Mac      Windows ──► Windows
```

不装驱动、不加声卡、不要管理员权限。两台机器在同一个局域网即可。

> 本文件同时是**交接文档**。接手的人先看「〇、当前状态」和「八、还没验证的事」。

## 〇、当前状态（2026-11-24，v3.0.2）

| 项目 | 状态 |
|---|---|

| 协议 | v5，与 3.0.1 及更早版本 **不互通**（v4 起拉流是「请求 → 质询 → HMAC 鉴权 → 应答」，再见包带会话令牌、冗余包 120 帧；v5 新增 NO_KEY 重配对包，修掉拉流包设备名错位、拒绝后冷却被绕过等问题） |
| 文档 | 本文件 + `docs/QUICKSTART.md`（两分钟上手/验证命令/已知限制）+ `docs/CHANGELOG.md`（设计与坑）+ `windows/用前必读.txt` |

v1 → v2 做了什么：

1. **双向 + 角色可选**：两端都能收能发（v1 只有 Windows 发、Mac 收）。
2. **连接稳定性**：自动发现、保活、回执、再见包、发送端锁定、设备热插拔自愈、睡眠唤醒恢复、自动缓冲、看门狗（详见第四节）。
3. **界面**：两端同一套设计（当时 400×560，v3 加到 400×720，明/暗跟随系统），状态卡 + 电平表 + 指标 + 设置。v1 是 Mac 菜单 + Windows 黑窗口。
4. **Windows 端重写**：命令行 `Sender.exe` → 带界面的 `AudioBridge.exe`，新增播放（接收）能力。旧源码留在 `build-old/Sender-v1.cs`。
5. 修掉的 v1 隐患见第七节。

v2 → v3 做了什么（本次）：

1. **接收端主动拉流**：接收端点「选择发送端…」，对方的程序就把声音送过来，不用跑到另一台电脑前操作。
   第一次拉某台设备会弹窗确认，同意后存为「受信任设备」，以后再拉不再打扰；对方也可以一键关掉「允许拉取」。
2. **丢包冗余**：发送端可选「丢包冗余」，每包尾部附上上一包的 PCM（流量约 ×2，`+1.5 Mbps`），
   丢一个包直接用副本补上，不再靠「保持末值 + 淡出」硬扛。
3. **多路接收混音**：接收端可打开「同时接收多路」，最多 4 台设备的声音混在一起（每路独立缓冲 + 独立重采样）。
4. **Windows 按程序采集**（Win10 2004+ 的 Process Loopback）：只送某个程序的声音，不送通知音和其他程序。
   系统不支持时自动回退到整机采集，不会没声音。
5. 协议升到 v4，两端都要更新。

## 一、怎么用

### Mac

```bash
./build.sh                         # 只需要 Command Line Tools，不用装 Xcode
open build/MonitorAudioBridge.app
```

> **从 1.x 升级**：先点菜单栏旧的喇叭图标 → 退出。旧版占着端口和单实例锁，不退的话新版会弹窗提醒并退出。

- 要求 macOS 14.2+（系统声音采集用的 Core Audio Process Tap 是 14.2 才有的）。
- 第一次**接收**：系统问「允许查找本地网络设备」→ 允许。
- 第一次**发送**：系统问「允许录制系统音频」→ 允许。拒绝了也不报错，只是发出去的是静音（界面会显示「当前没有声音在播放」并给出授权路径）。
  每次重新 `./build.sh` 后签名会变，系统可能再问一次。
- 关窗口只是收进菜单栏；菜单栏图标 → 退出音频桥 才是真退。

### Windows

把整个 `windows/` 文件夹拷到 Windows，双击 **`AudioBridge.exe`**（或 `启动.bat`，没有 exe 时它会用系统自带的 csc 现编一个）。

- 第一次运行弹防火墙 → 勾「专用网络」→ 允许。
- 关窗口收进托盘；托盘图标右键 → 退出。
- 改了 `.cs` 源码后跑 `重新编译.bat`。
- 详见 `windows/用前必读.txt`。

### 连起来

1. **要出声的那台**切到「接收」（默认就是），状态显示「等待发送端」。
2. **声音来源那台**切到「发送」，在「发送到」列表里点对方的名字。列表是自动发现的；
   没出现就在「手动输入 IP 地址」里填对方界面上显示的本机地址，回车。
3. 状态变成「正在发送 / 正在接收」，电平表在跳，就通了。

之后两边都勾「登录时自动启动」，开机即自动连回上次的设备，不用再碰。

## 二、界面说明

两端布局相同：

| 区域 | 内容 |
|---|---|
| 右上角 | 角色切换：接收 / 发送 |
| 状态卡 | 状态（等待 / 正在连接 / 已连接 / 正在接收·发送 / 对方没有回应 / 对方正忙 / 出错）+ 对端名字和地址 + L/R 电平表 + 四个指标 |
| 接收设置 | **接收来源（选择发送端 / 取消拉取）**、音量 / 静音（只影响本程序）、输出设备、缓冲档位、**同时接收多路**、本机名称与地址（可复制） |
| 发送设置 | 目标列表（自动发现）、手动地址、**允许其它设备拉取**、**受信任设备管理**、**丢包冗余**；Mac 多一个「发送时本机静音」，Windows 多一个「采集来源」（设备 / **按程序采集…**） |
| 底部 | 开始/停止、登录时自动启动、版本号 |

**指标怎么读**

- 延迟（估算）= 当前缓冲 + 输出设备延迟 + 约 10 ms 采集，不含网络传输本身（局域网通常 1–5 ms）。
- 网络抖动：包到达时间的波动。长期 > 10 ms 说明 Wi-Fi 不太行。
- 丢包：累计丢包率。
- 发送端看到的「对方缓冲 / 抖动 / 丢包」来自对方的回执，是**对方实际收到的情况**。

**接收来源**

- 「由发送端推送」：和 v2 一样，在对方的「发送到」里选这台电脑。
- 「主动拉取」：点「选择发送端…」，列出局域网里开着「允许拉取」的电脑，点一台即可；也可以手动输入 IP。
  拉取期间按钮变「取消拉取」，点一下会发「再见」让对方停发。
- 「同时接收多路」：打开后不再锁定单台，最多 4 台同时发声（混音）。收不到声音的那一路单独超时移除，不影响其它路。

**拉流的授权**

- 发送端第一次被某台设备拉取时弹窗：「『名字』请求接收这台电脑的声音」，允许后该设备记为受信任，
  并把发送目标切到它（如果当前是接收角色，会自动切到发送角色）。
- 发送端可以在「允许其它设备拉取」里整体关掉；「受信任设备」里可以逐台或全部移除。
- 拉取请求走发现端口（47832），不新开端口；被拒绝/对方正忙时会显示对应文案。

**缓冲档位**

| 档 | 值 | 适合 |
|---|---|---|
| 自动（默认） | 20–250 ms 动态 | 不想操心。按最近 10 秒最大包间隔 ×1.25 + 12 ms，涨得快降得慢 |
| 低延迟 | 20 ms | 游戏、两台都接网线或 5 GHz 信号很好 |
| 均衡 | 40 ms | 一般 Wi-Fi |
| 稳定 | 100 ms | 网络差、只听音乐 |

**电平表颜色**：绿 = 正常，琥珀 = 高于约 −6 dB，红 = 贴顶（源头已削波）。

**Windows 快捷键**：空格/回车 开始·停止，M 静音，←/→ 音量，Esc 收进托盘。

## 三、延迟与音画同步

总延迟 ≈ 采集（~10 ms）+ 网络（1–20 ms）+ 接收端缓冲（20–100 ms）+ 输出设备自身的延迟（Windows 端在设备缓冲里保持约两个周期，通常 20 ms 左右）。
自动档在良好网络下一般落在 50–70 ms。**画面在一台、声音从另一台出来时，声音会略晚**，看视频基本无感，
快节奏游戏能感觉到：选「低延迟」，两台都用 5 GHz 或网线。蓝牙耳机自身还有 150 ms+，这个没法靠本程序解决。

## 四、稳定性是怎么做的

| 场景 | v1 | v2 |
|---|---|---|
| 源头暂停播放（Windows loopback 没声音时不出数据） | 3 秒后误报「断开」 | 发送端每 0.5 s 发保活，显示「已连接 · 当前没有声音」 |
| 发送端不知道对方收没收到 | 只能看自己发了多少 | 接收端每 0.5 s 回执（收包/丢包/抖动/缓冲），收不到回执 2.5 s 后明确提示「对方没有回应」并列出排查项，同时**继续发**，对方一上线自动续上 |
| 一方退出 | 另一方等超时 | 发「再见」包，对方立刻更新状态 |
| 两台同时往一台发 | 两路声音绞在一起 | 接收端锁定先来的那台，后来的收到「对方正忙」 |
| 对端 IP 变了（重连 Wi-Fi、DHCP） | 要重新抄 IP | 每台有持久化的设备号，发现信标里认出同一台，自动跟到新地址 |
| 接收端插拔耳机 / 切换输出设备 | Mac 上直接没声，要手动「重新开始接收」 | 监听配置变化，0.3 s 后自动重建播放引擎；钉住的设备不在线时先用系统默认，回来后自动切回 |
| 发送端切换默认播放设备 | Windows 端直接抛异常退出 | 每秒检查默认设备，变了就重开采集；任何采集/播放错误都是「收拾干净 → 等 0.5 s → 重开」 |
| 睡眠唤醒 | 可能卡死 | 唤醒后整体重启网络和音频 |
| 发送端重启 | 等超时才能重新锁定 | 同 IP 换端口即视为重启，立即换锁 |
| 发送端换输出设备导致采样率变化 | 一小段变调 | 采样率变化即清空缓冲重新对齐 |
| 迟到/重复的包 | 被当成「发送端重启」，时间轴错位 | 丢弃并计数 |
| 端口被占 / 引擎意外停了 | 一直错着 | 看门狗每 3 秒重试 |
| Windows 定时器精度 15.6 ms | `Sleep(2)` 实际睡 15 ms，包成坨发出，接收端被迫加大缓冲 | `timeBeginPeriod(1)` + MMCSS「Pro Audio」线程优先级 |
| Windows 对方没开时 UDP 收到 ICMP 不可达 | 可能抛 10054 | 关掉 `SIO_UDP_CONNRESET` |
| 偶尔丢一两个包（Wi-Fi） | 保持末值 + 淡出，能听出「咯」一下 | 开「丢包冗余」：每包尾部带上一包副本，丢包直接补，`lost` 不增加、`recovered` 计数 |
| 想同时听两台电脑 | 只能锁定一台 | 开「同时接收多路」：每一路直接在播放回调里按自己的采样率取数，相加后限幅输出 |
| 想主动听另一台，但不想走过去点 | 无 | 接收端「选择发送端…」拉流；首次需对方确认，之后凭密钥静默接受 |

仍然是**裸 UDP、不重传、不加密**：局域网里这是延迟最低的做法。默认丢的包用「保持末值 + 5 ms 淡出」盖过去；
打开「丢包冗余」后，单包丢失由上一包副本补齐（连续丢两个以上仍会 conceal）；带副本的包缩到 120 帧（984 字节），不会被 IP 分片。
拉流的鉴权走「随机数 + HMAC-SHA256 截断 16 字节」，长期密钥只在首次配对时下发一次、之后不再重复上线；音频本身仍是明文。

**两端是同一套逻辑的两份实现。** 带 ★ 的文件改一边就要改另一边：协议字段、状态文案、超时阈值、缓冲算法。
`Theme` 的色值也是两边各一份（`MainView.swift` / `Ui.cs`）。

### 设计上的几个决定

- **Windows 用 C# 5 + WinForms 自绘**：为了「拷过去就能跑」——Win10/11 自带 .NET Framework 4 和 csc.exe，不用装 SDK。
  代价是不能用 `$""`、`?.`、`=>` 成员、`out var` 这些新语法。界面全部自己画（包括图标），所以不依赖系统图标字体。
- **Mac 采集用 Process Tap 而不是 ScreenCaptureKit / 虚拟声卡**：不需要屏幕录制权限，不装驱动。
- **关窗口不退出**：这是个常驻工具。Mac 有窗口时显示 Dock 图标，关窗口后只留菜单栏。
- **静音门限**：连续 0.5 s 全零就停发音频包（保活照发）。省流量，也让两个平台行为一致（Windows loopback 天生如此）。

## 六、协议（v5，小端；与 v4/3.0.1 不互通）

端口：音频 **47831/udp**（接收端监听），发现 **47832/udp**（两端都监听，广播）。
所有包以 `"MAB1"` + `type(u8)` 开头。

**type 1 音频**（发送端 → 接收端）——与 v1 相同

| 偏移 | 类型 | 含义 |
|---|---|---|
| 5 | u8 | 声道数（1 或 2） |
| 6 | u32 | 采样率 |
| 10 | u32 | 包序号 |
| 14 | u16 | 每声道帧数（普通 240；开冗余时 120，≤4096） |
| 16 | u64 | 发送端单调时钟 ns（只用来算抖动）。v4 起最高字节被借作冗余标志，接收端按 56 位读 |
| 23 | u8 | bit0「本包尾部带上一包的 PCM 副本」（丢包冗余） |
| 24 | … | Int16 交织 PCM；带冗余时是 `本包 PCM + 上一包 PCM`，长度翻倍 |

**type 2 保活**（发送端 → 接收端，0.5 s 一个）：5–23 同音频头（帧数 0）· 24 `id u64` · 32 `nameLen u8` · 33 `name utf8`

**type 3 回执**（接收端 → 音频包的来源地址，0.5 s 一个）

| 偏移 | 类型 | 含义 |
|---|---|---|
| 5 | u8 | 标志：bit0 正在出声 · bit1 已静音 · bit3 正忙（已在接收另一台） |
| 6 | u16 | 当前缓冲 ms |
| 8 | u32 | 已收包数 |
| 12 | u32 | 丢包数 |
| 16 | u32 | 抖动（微秒） |
| 20 | u16 | 目标缓冲 ms |
| 24 | u64 | 设备号 |
| 32 | u8 + utf8 | 设备名 |

**type 4 再见**（任一方向）：5 `ver` · 8 `token u64`（本次会话令牌；发送端用自己的会话令牌比对，0 表示无令牌，按 v4 规则一律忽略）

接收端只接受这样的再见：长度 ≥ 16、自己正在发送、来源 IP 等于当前目标 IP、令牌等于本次会话令牌。四者缺一不停发。

**鉴权（v4 核心改动）**：长度密钥不下发。首次配对由用户弹窗确认，发送端在 type 6 里下发新密钥（只此一次）；之后受信任设备拉流走质询-应答，不再传输密钥本体：

`nonce` 24 字节输入 = `nonce u64 ‖ requester u64 ‖ senderID u64`，`mac` = `HMAC-SHA256(密钥 8 字节大端, 输入)` 的前 16 字节。

**type 5 拉流请求**（接收端 → 发送端的发现端口 47832）

| 偏移 | 类型 | 含义 |
|---|---|---|
| 5 | u8 | 版本（4） |

| 24 | u8 + utf8 | 请求方设备名（**v4 起不再带密钥**） |

| 偏移 | 类型 | 含义 |
|---|---|---|
| 5 | u8 | 版本（4） |

| 32 | u8 + utf8 | 发送端设备名 |

**type 8 拉流鉴权**（请求方 → 发送端）

| 偏移 | 类型 | 含义 |
|---|---|---|
| 5 | u8 | 版本（4） |
| 6 | u16 | 请求方监听的音频端口 |
| 8 | u64 | 质询里的 nonce |

| 32 | 16 字节 | `HMAC-SHA256` 截断值（见上） |
| 48 | u8 + utf8 | 请求方设备名 |

**type 9 「我没有你的密钥」**（请求方 → 发送端；首次配对的应答包丢了、或信任表被删时）

| 偏移 | 类型 | 含义 |
|---|---|---|
| 5 | u8 | 版本（5） |
| 6 | u16 | 请求方监听的音频端口 |
| 8 | u64 | 请求方设备号 |
| 16 | u64 | 发送端设备号 |
| 24 | u8 + utf8 | 请求方设备名 |

发送端只接受「刚给这个设备号、这个来源 IP 发过质询」的那种：作废旧密钥后重新弹窗配对。
别人从另一个 IP 冒用设备号发这个包不会动信任关系。

**type 6 拉流应答**（发送端 → 请求方）

| 偏移 | 类型 | 含义 |
|---|---|---|
| 5 | u8 | 版本（4） |
| 6 | u8 | 结果：0 允许 · 1 允许且附带新密钥 · 2 拒绝 · 3 正忙 · 4 未开启 · 6 等待对方在界面上确认 |
| 7 | u8 | 标志：bit0 带密钥 · bit1 带会话令牌 |
| 8 | u64 | 请求方设备号（回显） |
| 16 | u64 | 发送端设备号 |
| 24 | u64 | 会话令牌（后续再见要带同一个值） |
| 32 | u64 | 新密钥（仅首次配对、bit0 置位时有效） |
| 40 | u8 + utf8 | 发送端设备名 |

请求方只接受「来源 IP 等于本次拉流目标 IP、且自己正处于请求中」的应答；已连上后重放的旧应答会被忽略。伪造的请求（哪怕设备号对得上）不会改变发送目标，也不会拿到密钥。

**type 16 信标**（广播到 47832，1 s 一个）：5 `ver` · 6 `role`（0 空闲 1 发送 2 接收）· 7 `platform`（1 Mac 2 Windows）· 8 `state`（0/1 是否已连上）· **9 `caps`（bit0 允许拉取 · bit1 正在混音）** · 10 `audioPort u16` · 12 `id u64` · 20 `nameLen` · 21 `name`

设备名最长 60 字节 UTF-8。设备号首次运行随机生成后存盘（Mac：UserDefaults `deviceID`；Windows：settings.ini）。
4.5 s 没收到信标的设备从列表移除。

## 九、已知限制

- Windows 发送端没有「本机静音」：loopback 抓的是那个播放设备上的声音，把设备静音在部分驱动上会连采集一起静掉。
  （按程序采集也一样：静音那个程序就等于不送。）
  变通：让 Windows 默认输出走显示器 HDMI，把显示器音量拧到 0。
- 多声道（5.1/7.1）只取前左/前右，不做降混。
- 发现靠广播，过不了路由器 / VPN / Tailscale / 开了 AP 隔离的公共 Wi-Fi——用手动 IP（AP 隔离则完全不通）。
- 音频不加密、不鉴权。同一局域网内知道协议的人可以往接收端推声音，也能收到发给广播地址的信标（只含设备名、角色、能力位）。
- 拉流的授权是「设备密钥」级别：接受过一次就长期记住，密钥以明文存在本机（Mac `trust.json` / Windows `trust.ini`），
  不是加密的证书体系。日常的拉流请求用「随机数 + HMAC」证明持有密钥，密钥本身不再每次上线；但局域网内仍可重放
  5 次以内的错误凭据（同一个 IP 连续错 5 次才冷却 30 秒）。别在不信任的网络上用；换人用这台电脑前记得「全部移除」。
- 多路混音同时最多 4 路，混音时统一按 48 kHz 输出（44.1 kHz 来源会重采样）。
- 按程序采集只在 Windows 10 2004+ 有效；系统不支持时回退整机采集，界面会显示「整机（按程序采集不可用）」，
  原因写进 `error.log`。设置里只存**程序名**，重启后按名字重新找进程；找不到就当整机采集。
- Windows 自绘界面对读屏软件不友好（Mac 端用的是标准 SwiftUI 控件，有无障碍标签）。
- Mac 每次重新编译后是新的 ad-hoc 签名，系统可能重新询问权限。长期自用可以换成固定的自签名证书。
- 16-bit 传输。量化底约 −96 dB，实际听不出，但不是无损的 24/32-bit。

## 十、可以继续做的（未实现，按性价比排）

1. **真机验收**：第八节前 5 条都需要真人 + 真机，优先级高于任何新功能（尤其 Windows 真机整体和按程序采集）。
2. **Opus 编码档**：1.5 Mbps → 128 kbps，适合跨 VPN / 热点；代价是 +5–20 ms 延迟和一个编解码依赖。
3. **丢包补偿再进一步**：现在是「每包带上一包副本」。连续丢 2 包以上仍会 conceal，
   可按接收端回执里的实时丢包率自适应开关冗余；或做波形外推（用前两包预测）。
4. **混音的可视化与音量**：目前每路固定 1.0 增益，不能单独调某一路的音量/静音。
5. **发现层的鲁棒性**：广播过不了路由器 / VPN；可以做 mDNS 或让接收端也发「我在找」的信标。
6. **Windows 发送端的「本机静音」**：用 `IAudioEndpointVolume` 的 session 级别静音做不到不中断采集，
   需要虚拟声卡或按程序采集 + 单独静音那个程序，暂不做。
7. 固定证书签名 + 公证（Mac）、打成单文件安装包（Windows）。
8. 协议层加密（现在只有设备密钥做授权，音频是明文）。

## 附：音质（沿用 v1 的测量，算法未变）

`RingBridge` 的时钟伺服：填充误差先做约 2.6 s 平滑，再乘 0.05，速率微调上限 ±0.15%（±2.6 音分）。

断流时读指针只进不退并淡出 20 ms（早期会把最后 40 ms 反复重放成「嗒嗒嗒」），`--selftest` 里有硬指标防回归。
